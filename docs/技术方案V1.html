0. 本轮新发现的问题

你这一轮的回答把需求基本冻结了，但其中三条里各藏着一个需要先定掉的坑。

问题 1：打卡的触发方式没定义，而且视觉方向是反的。

你写的是「让景点在地图上点亮，用户到地点打卡，打卡的地点变暗」。这里有两件事：一是系统怎么知道用户「到了」——是用户自己点一下按钮，还是靠手机定位自动判定？这决定要不要申请浏览器定位权限、要不要强制 HTTPS、以及弱信号下的兜底策略。二是视觉语义反直觉：绝大多数产品的习惯是「未完成=灰暗，完成=点亮」，你这里是反过来的。用户第一次看到「亮点」很可能以为已经去过了。建议改成：未打卡 = 空心标记，已打卡 = 实心带勾。详见第 8 节。

问题 2：「距离按直线算」只能用于粗筛，地图上画的路线必须用真实路径。

直线距离（两点连线的球面距离）算得快，但会选出「直线很近、实际要绕 40 分钟」的点。典型场景：上海选到浦东和浦西各一个点，直线 3 公里，实际过江要绕；重庆两江四岸、有山体阻隔的城市更明显。正确做法是用直线距离做排序和聚类，用高德路径规划生成最终路线和通勤时间——反正地图上要画线，本来就得调路径规划。另外建议加一道校验：相邻两点实际通勤时间超过 40 分钟就换掉一个点。

问题 3：「不算每个景点玩多久」之后，「时间轴」就名不副实了。

第 2 轮你确认了「按天时间轴 + 地图联动」，但这一轮说不用计算游览时长。两者不能同时成立：没有时长就无法排出「9:00–11:00 游览 A」这样的具体时刻。可行的形态是时段分组的顺序列表——上午 1 个景点、午餐、下午至晚上 1–2 个景点，只标顺序不标钟点。需你确认接受这个降级。

问题 4：「只支持单城市」没有回答境内还是境外。

高德地图的数据基本只覆盖中国境内，境外城市既没有 POI 也没有路线。所以「单城市」还需要补一句：第一版是否只支持中国境内城市？如果是，Google Places 和 OpenStreetMap 就可以从 V1 里彻底删掉，方案更干净；如果境外也要，就得再补一套数据源和地图兜底，工作量显著增加。本方案按仅境内编制。

2. 系统架构

图 1 · 系统架构。前端不持有任何密钥，全链路只经服务端转发。

两套高德 Key，用法不同，别混。浏览器端加载地图用 Web 端（JS API）Key，需要配置域名白名单；服务端查 POI、路径、天气用 Web 服务 Key。前者必须暴露给浏览器，所以要靠域名白名单保护；后者只能待在服务端，绝不能下发到前端。

5. Agent 工具清单

CodeBuddy Agent SDK 在后端运行，通过 function calling 调用下面这些工具。工具本身是薄封装，真正的活儿在高德与本地计算里。

工具名底层接口作用与关键参数
geocode_city高德 地理编码城市名 → adcode 与中心坐标
search_spots高德 POI 周边/关键字搜索按锚点坐标 + 半径搜候选景点，取 rating、opentime_today、typecode；分页上限 200 条
search_stay高德 POI 关键字搜索按预算与偏好推荐住宿候选（供「还没定」时兜底）
search_restaurants高德 POI 周边搜索在相邻两景点坐标之间取中点，半径内搜 types=050000，按 rating 与 cost 排序
straight_distance本地计算球面直线距离，用于排序与聚类（注意：仅用于粗筛）
plan_route高德 路径规划生成真实路线与耗时，供地图绘制与通勤校验（步行/驾车/公交）
get_weather高德天气 → Open-Meteo 降级行程日期在 4 天内走高德，超出自动切 Open-Meteo，再超出则气候均值
save_itinerary本地写库把结构化行程落库，返回 trip_id

别让模型自由发挥时直接产出坐标。所有坐标必须来自工具返回的高德 POI，模型只负责「选哪些、怎么串」，不负责「编造经纬度」。否则地图上会出现飘到海里的标记。这是这类应用最常见的翻车点。

6. 每日行程生成流程

图 2 · 每日行程生成算法。第 2–4 步用直线距离（快），第 7 步必须用真实路径（准）。

第 4 步的分天规则（对应你定的约束）

  • 每天景点上限 3 个，餐厅不计入该上限。
  • 时段分配：上午 1 个景点 → 午餐 → 下午至晚上 1–2 个景点 → 晚餐。
  • 若当天只有 1 个景点（如首日抵达），餐厅退化为「景点周边就近推荐」，不再要求夹在两景点之间。
  • 首日与末日建议按半天强度处理（景点数可降为 1–2 个），这一点需你确认。
  • 聚类时同一天的 3 个景点应落在同一片区域内，而不是满城对角线跑。

8. 打卡机制设计

三种可选实现，差别在「系统怎么确认用户到了」：

方案做法优点代价
A 手动打卡点击卡片上的「我已到达」零依赖，最快落地不防作弊（个人工具其实不需要）
B 定位打卡浏览器定位取坐标，与景点坐标距离小于阈值即判定到达体验好，不需要用户操作需 HTTPS 与定位授权；室内精度差，阈值要放宽到 300–500 米；被拒绝授权要能降级
C 混合（建议）默认手动，用户可在设置里开启「定位自动打卡」照顾两种场景，不强制实现量略大，但只是一层判定分支

视觉语义建议改掉。你原本的设计是「点亮 = 未打卡，变暗 = 已打卡」，与主流习惯相反，用户会误判。建议：
· 未打卡景点 = 空心圆点标记 + 常规颜色
· 已打卡景点 = 实心标记 + 对勾角标 + 卡片置灰
· 当天推荐中的当前目标 = 放大或加脉冲效果区分
另外建议默认只显示当天的标记，否则 7 天行程 20 多个点全铺在地图上会糊成一片。

隐私提示：如果采用定位打卡，位置数据只用于「是否到达」这一瞬间的判定，不记录轨迹、不落库原始坐标。这一点应写进隐私政策。

10. 合规检查清单

  • 地图合规：境内地图必须使用具备甲级测绘资质的地图服务（高德符合），并保留审图号展示；不得自行绘制或篡改国界线与行政区域，不能拿一份 GeoJSON 自己画中国地图。
  • 数据来源：只用高德官方 Web 服务 API，不抓取小红书、美团、大众点评。已确认这三条路或不存在、或需企业资质与高额保证金。
  • AI 内容标注：行程由模型生成，页面需标注「内容由 AI 生成，营业时间与价格请以实际情况为准」。高德 POI 的营业时间字段缺失率不低。
  • 密钥托管：主密钥放环境变量，不提交仓库；AES-256-GCM 加密；日志脱敏；设置页如实告知用户密钥由服务端加密存储。
  • 个人信息：收集用户名与行程数据，面向公众上线需隐私政策、用户协议与 ICP 备案。
  • 定位权限：若启用定位打卡，需明确告知用途且可随时关闭。
