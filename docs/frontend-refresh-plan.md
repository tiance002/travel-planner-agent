# 旅游助手前端视觉改版规划

日期：2026-09-28。范围：现有 Web 页面视觉与信息层级规划；本文件不代表视觉代码已实施。稳定性修复优先，P1-5 的 partial 实际入口由当前修复任务落实。

## 目标与约束

用户已明确选择「清爽旅行风：暖白底、自然色、清晰卡片」。面向正在规划或查看旅行的用户，让目的地、日期、每天安排和下一步操作可以快速找到。以内容可读、移动端可达和状态可信为成功标准。

保留 React、Ant Design、现有路由、主题开关、地图联动与业务接口。不替换组件库，不进行大规模 antd 重构，不新增照片服务或装饰动画。假设本轮视觉方向以白天模式为主，黑夜模式继续保留并使用相同信息结构。完整视觉改版尚未实施；本轮浏览器只验收业务状态卡、操作可达性和进度文案，下面的溢出风险仍需在视觉实施时实测。

本轮稳定性工作已先落地 P1-5 所需的状态入口，视觉重构仍按后文阶段计划延后：详情和新建页优先读取服务端 `completedDayCount` / `missingDayIndexes`，`partial` 始终显示安全补缺操作；详情刷新后可继续处理已持久化的 review 卡，并可在 waiting/recovery 阶段取消后保留已落库日期和打卡。已有日期的重新规划入口会创建新草稿，原行程不被覆盖。以下关于书签、线圈本、固定高度与移动布局的诊断仍是待实施规划。

## 设计方向与取舍

考虑三种方式：只改主题 token 成本最低，但无法解决书签、便利贴和移动布局；保留完整手帐风能延续旧风格，但不符合用户希望的清爽；推荐「旅行计划卡片」：保留目的地、出发日期、日次这些真实旅行信息，通过轻边框和明确间距组织。

设计的记忆点放在每天路线的时间轴：时间、地点、通勤连接形成一条可读的旅行路径。列表、表单、导航保持安静。暖白是用户指定的底色；不额外叠加陶土装饰、衬线大标题、纹理、渐变或模拟纸张来强化模板感。卡片只承担行程、日程、住宿候选等实际内容分组；普通字段与段落不逐个套卡片。

### 基础 token

| token | 色值 | 用途 |
| --- | --- | --- |
| `canvas` | `#F8F7F3` | 全站暖白背景 |
| `surface` | `#FFFFFF` | 主卡片、输入区与浮层 |
| `ink` | `#263A32` | 正文与标题；次级文字可由同色派生，须实测对比度 |
| `border` | `#DEE5DF` | 分隔和非交互卡片边框 |
| `forest` | `#2F7058` | 主按钮、当前导航、日次选中；浅底由此色低透明度派生 |
| `lake` | `#416F8B` | 地图关联、交通信息与普通生成进度 |

六色是基础品牌色，不替代 antd 的 success/warning/error 语义色。partial 使用 warning，failed 使用 error；色彩必须同时带文字或图标。所有正文、placeholder、按钮与焦点在真实背景上检查对比度；正文至少 4.5:1，交互边界及焦点至少 3:1。

字体采用 `"PingFang SC", "Microsoft YaHei", "Noto Sans CJK SC", system-ui, sans-serif`，不要求联网加载字体。页面标题桌面 28px/600、移动 24px/600；模块标题 18px/600，正文 15px/400、行高 1.6；辅助说明 13px，避免现有 11px 密集字段。时间和金额使用 tabular-nums，标题与文本均左对齐。

间距基于 4px：字段内 8、相关信息 12、卡片内容 20（移动 16）、卡片间 16、模块间 24、页面边距桌面 32/移动 16。内容最大宽 1200px；表单阅读区 720px；长说明控制在约 36 个汉字一行。卡片圆角 12px、输入框/按钮 8px；常规卡片仅细边框，浮层使用 antd 标准阴影，减少全站大面积投影。

## 页面布局

### 全局框架

桌面 ≥1024px 保留侧栏与用户信息，但侧栏纯净表面、主导航不占用风景横幅，内容按页选择滚动模式。768–1023px 导航折叠为抽屉，内容完整占宽；<768px 顶部保留菜单入口、应用名与账户入口，主题切换移入抽屉。详情仅在桌面且有足够可用高度时采用双栏内部滚动；窄屏恢复自然页面滚动。桌面布局高度由 flex 的剩余空间决定，避免固定 `100vh - 248px` 假定概要高度恒定；支持 `100dvh`。

### 我的行程 TripList

标题与「新建行程」同一行，下面直接显示卡片列表。每条卡片左侧以目的地文字为主要识别，标题与状态同一层，出发日期/天数/人数在下一层，住宿信息独立一行。删除放到独立操作入口，保留确认。

```text
我的行程                                  [新建行程]
┌─────────────────────────────────────────────────┐
│ 杭州  西湖与老城三日游                 [部分完成] │
│       10月2日出发    3天    2人                  │
│       住宿：已选酒店               [查看行程] [更多]│
└─────────────────────────────────────────────────┘
```

手机为单列全宽卡片：标题允许两行，状态另占明确位置，日期/人数自然换行，主入口与更多操作保持至少 44px 触控区域。卡片入口使用链接或按钮语义并能键盘访问，避免当前纯 div 点击。无行程用一句「还没有行程」与「创建第一个行程」；加载保留 Skeleton；列表读取失败需呈现错误和重试，不能看起来像成功读取的空列表。

### 新建行程 NewTrip

以真实的三个阶段呈现「旅行信息 → 住宿安排 → 生成行程」。桌面主体 720px 表单，右侧可用窄栏显示已经填写的目的地、日期、人数摘要；若空间不足摘要回到页面顶部。第一阶段分为旅行信息、偏好与预算、额外需求，分区用正文标题和留白，取消牛皮纸签。高级或解释性内容折叠，首屏先显示需要填写的字段。

住宿地图与酒店结果桌面并列；手机先显示搜索/候选，再显示可折叠地图，至少保留 280px 地图高度。下一步的可用性仍以原有目的地解析和表单校验为准。移动端单列字段、页面滚动，底部操作区可 sticky 但必须预留安全区和底部空间，不能遮住最后一个字段；键盘打开时确保当前字段可见。

生成阶段顶部只出现一个主要状态面板：已排好天数、当前在做什么、下一步操作。规则说明和天气放到辅助区；行程 ID 与行政区编码移到「详细信息」，不与目的地同等醒目。生成完成后主操作直接「查看行程」进入当前已保存 tripId 的详情，返回修改是次操作。

```text
新建行程
旅行信息  →  住宿安排  →  生成行程
┌─────────────────────┐  ┌────────────────┐
│ 已排好 2/3 天        │  │ 杭州 / 3天 / 2人│
│ 第3天需要继续安排    │  │ 日期 / 住宿摘要 │
│ [补齐剩余天数]       │  └────────────────┘
│ [从头重新生成]       │
└─────────────────────┘
```

### 行程详情 TripDetail

概要先展示标题、状态、目的地和日期，住宿与人数作为次级信息。状态提示按内容自然增长，不能把固定高度的地图挤出屏幕。桌面概要下面为日程与地图双栏：建议日程约 52%、地图约 48%，无需为装饰标题强制等宽。每日卡片包括时间、地点、停留建议和打卡/换一个；通勤作为两个地点之间的连接行，地图选中项与日程选中项使用相同 forest 强调。

```text
杭州三日游 [已完成]                        [返回列表]
10月2–4日   2人   住宿名称
[第1天 10/02] [第2天 10/03] [第3天 10/04]
┌───────────────────────┐ ┌───────────────────────┐
│ 09:00  地点与停留建议  │ │ 当天路线              │
│        已打卡 / 换一个 │ │ [步行] [公交] [驾车]  │
│ ↓  步行约15分钟       │ │                       │
│ 12:00  午餐           │ │        地图           │
└───────────────────────┘ └───────────────────────┘
```

手机默认日程列表；日次可横向滚动但不带动整页横向溢出。地图放在「查看当天地图」可展开区或切换面板中，保留当天选择，切换后刷新地图尺寸；日程全长可滚，不再叠加线圈和内部视口限高。路线方式按钮允许换行，换一个抽屉在手机全宽。

## 真实生成状态与操作入口

以下为阅读时状态，后续稳定性修复应与本规划对齐，不把视觉方案当成已经存在的功能。

| 实际条件 | 展示名称 | 主要操作 | 当前证据/问题 |
| --- | --- | --- | --- |
| `draft` | 草稿 | 开始生成 | 列表和详情已有识别 |
| `generating` 且没有 review | 正在生成 | 查看当前进度 | 轮询存在；后台仍工作时不能展示成失败 |
| `generating` 且有有效 review | 等待你确认 | 确认采用 / 选择方案 / 调整后重排 | 新建页和详情都解析持久化 `genReview`，裁决请求带 `genReviewId`；详情刷新后仍可操作，waiting/recovery 可取消 |
| `ready` | 已完成 | 查看行程 | 使用真实服务端状态，不以进度 100% 推断完成 |
| `partial` | 部分完成 | 补齐剩余天数或完成收尾 | 列表、新建页和详情统一显示 partial；进度使用服务端 `completedDayCount` / `missingDayIndexes`，详情的按钮调用当前行程 `generate{mode: continue}`；即使缺失日为空也保留幂等收尾入口 |
| `failed` | 生成失败 | 按可恢复数据提供继续或重新生成 | 已排好内容需保留可见；没有已排天数或缺失日为空也不能永久困在提示中 |
| `failed` + `genRunPhase=commit_pending` | 安排已生成，保存未成功 | 重试保存已生成安排 | 使用 `generate{mode: continue}` 消费服务端持久化结果，不重新调用模型；当前前端不声称存在其他提交恢复阶段 |

review 是生成中的等待阶段，不是错误，必须暂停“还在自动推进”的动效与文案。单方案突出当天摘要、确认和调整；双方案桌面并列、手机堆叠，评分/驾车/公交耗时明确注明来源和未知值，未知不能写成 0。正在提交时阻止重复裁决；失败保留候选与反馈内容。服务端 review 载荷不合法时应有可理解的提示，避免永久显示生成中却无动作入口。

partial 的进度以实际已保存日数表示，已保存内容可查看；缺失日序使用服务端派生值，不把「完成数+1」当成缺失日索引。统一 warning 表示部分完成，failed 才使用 error。列表、生成页、详情状态文案一致；详情和新建页都提供作用于原行程 ID 的真实补齐按钮，即使 0 天已落库或缺失日为空也保留入口，后端以幂等 continue 完成最终收尾。`commit_pending` 代表模型结果已保存但日期提交尚未完成，继续操作只重试保存，不重新调用模型。已有日期的重新规划会走新草稿，避免后端 restart 保护触发后让用户失去可用操作。

P1-5 验收重点：从列表打开 partial 行程后可以在原行程上触发补齐；不要求用户重新填表，不丢失已有安排或打卡。生成页与详情的状态说明和操作位于同一处。重新规划通过新草稿保留原行程，风险说明来自真实后端行为，不能用视觉样式暗示已保存内容一定保留。本轮已用隔离本机 fixture 验证 4/5 缺第 2 天、0/5、waiting review（approve/choose 带 reviewId）、recovery 取消、missing 为空时的收尾按钮、`commit_pending` 保存重试、副本切换旧响应保护，以及 ready 3/3 的完成文案与 100% 进度。execute 另用独立临时数据库和临时账号完成真实 API 的 review waiting→reject/replan→partial→continue→ready 链，并完成 77/77 的真实浏览器 smoke；这些证据不涉及开发库原用户。完整视觉改版仍未实施。

## 实施阶段

1. **稳定性与入口先行**：完成 P1-5，核验 partial 原行程补齐、状态映射一致、review 等待态和失败可恢复行为。此阶段只做必要状态/入口修复，避免同时大改布局。
2. **主题与框架**：在 `main.tsx` 的 ConfigProvider 和 `index.css` 统一六色、字体、间距；导航采用纯表面；落实移动导航和页面滚动。主题状态沿用 `theme.tsx`，CSS 与组件不新增独立主题来源。
3. **列表与新建**：调整 `TripList.tsx` 卡片语义和结构、`NewTrip.tsx` 三步信息层级与移动表单；保留原校验、请求及生成状态管理。对 `paper.tsx` 只替换视觉职责，保持业务调用可逐步迁移，避免为改外观重写所有组件。
4. **详情与状态**：调整 `TripDetail.tsx` 双栏/手机地图切换、日程路线样式；将 review 与 partial 操作收敛成状态面板。未核验过的服务端恢复能力单独标注并补验证，再开放对应按钮。
5. **视觉与功能验收**：用真实状态截图检查每个页面白天/黑夜、短标题/长标题、无住宿/已选住宿、长反馈和七天行程；回归关键流程后交付。

## 验收清单

- 在 375、390、768、1024、1440px 宽度下，页面无横向溢出，菜单、日程底部、地图与所有操作可达；用 200% 浏览器缩放再检查一次。
- 桌面日程与地图联动稳定；手机滚动到最后一站、打开地图、切日次、切交通方式，内容不裁切、不被固定操作遮挡。
- 新建流程填写、解析目的地、选住宿、普通生成、逐天确认、双方案选择、驳回重排、完成后打开当前详情均可操作；新增视觉不改变接口语义。
- partial 在三个页面都叫「部分完成」，指出实际缺失日；原行程补齐后状态与日程刷新正确；failed 不伪装成草稿；review 不伪装成仍在自动推进。
- 键盘可完成导航、表单、卡片入口、review 与弹窗；焦点可见，触控操作至少 44×44px；减弱动态偏好下不播放装饰动画。
- 正文对比度达标，状态有文字解释，加载/空/错误三者可区分；无数据地图、未知路线与超出天气预报范围有真实提示。
- 白天/黑夜主题切换保持可读、不混用浅色底与浅色文字，弹窗和下拉项同样通过验收。
- 视觉代码实施后再执行项目现有构建与相关功能测试；本规划文档不声称以上验收已经完成。
