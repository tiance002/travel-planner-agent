一、需求演进史：从一句话到 15 个版本

原始需求只有一句话：「做一个 AI 旅游规划应用，用户输入目的地和天数，AI 帮忙排行程，能看地图、能打卡。」——这句话离能落地还差得远，之后经历了 15 轮「提出 → 实现 → 发现问题 → 重新明确」的循环。把这条演进线记下来，比记最终代码更重要，因为它展示了真实需求是怎么长出来的。

阶段提出 / 明确的需求影响的设计决策
原始需求AI 排行程 + 地图 + 打卡确定要做 Web 应用
P1–P3登录注册、新建行程向导、生成行程用户名+密码登录；四步向导雏形
P3 明确砍掉 Electron 桌面封装，纯网页；第一版只做中国境内单城市砍掉跨平台打包；地图服务选定高德（境内唯一合规选项之一）
P4模型接入方式：用户自带 API Key（BYOK）服务端持有主密钥加密存储用户的 Key；只支持「OpenAI 兼容接口」

P4 决策每日景点上限 3 个；不计算游览时长时间轴降级为「时段分组顺序列表」，排不出具体钟点就分组展示
P5 决策坐标铁律：地图坐标只准来自高德 POI 返回值，模型绝不编造经纬度建立 POI 登记表 registry，行程只准引用登记过的地点

P8「换一个」候选替换；行程卡片标签化半径梯度 1500/3000/5000m 搜同类候选，按两段通勤之和排序取前 6
P8 决策选点准入硬规则：景点评分 < 4 直接剔除、餐厅放宽 3.5、评分缺失一律放行（否则误杀免费公园）纯函数规则层 spot-rules.ts，可单测
P8 决策营业时间必须与所排时段对得上（重叠 ≥ 60 分钟）；「到达后剩余 < 3.5 小时」只提示仓促不剔除；餐厅完全不校验高德营业时间数据最不准，硬卡会卡死行程
P8 决策行程体裁五种：normal / theme_park / hike / night_hike / recovery；夜爬次日强制恢复日规则表优先 + 模型提议兜底 + 统一过黑名单拦截（否则模型提议路径绕过用户约束）
P9纸质手帐主题：书签列表、线圈本、便利贴、胶带；白天棕 / 黑夜灰全局 token 承载纸质感，不逐页写背景色
P9 反馈书签太窄（加厚到 5/3 = 91px）、便利贴改恒为浅底深墨、去掉悬停晃动、设置页字段居中发现并修复「底色读 DOM、墨色读 React 状态」的一帧错位（浅底配浅字）
P10滚动条抖动、下拉带动整页滚动 → scrollbar-gutter + overscroll-behavior；表单限高内滚布局策略定型：「外壳固定 + 内容区内滚」
P11–P15用户主动要求：用 LangGraph 重写编排 + 多版本迭代；逐天确认要能驳回并给意见；并行择优要两案对比由用户挑；通勤要分驾车/公交两种；候选通勤不能是 0；删除手写版LangGraph V1–V5；genReview/genDecisions 字段；amap 层三处修复；最终单路径
规律总结：几乎所有后来的复杂度都源自两类反馈——①数据不可信（评分缺失、营业时间乱、路线查询偶发失败），于是建了一层层「宁缺毋错」的防御；②用户要掌控权（换一个、确认/驳回、两案挑选），于是把全自动流程改造成了人机协作。

三、技术栈：每一项是什么、为什么选它、怎么用的

3.1 前端

技术一句话定义 + 类比在本项目怎么用
React 19.3前端框架，负责「数据变了界面自动跟着变」。类比：你只管改台账，黑板自动重抄。
注意 Hook 铁律：所有 use 开头的函数必须放在任何提前 return 之前，否则白屏（踩过，见第八章）。
全部页面组件；状态用 useState/useRef；生成进度用 setTimeout 轮询（每 2.5 秒问一次后端，而不是挂一个长请求）
Vite 8前端开发服务器+打包器。类比：开发时现做现上的后厨，打包时才备整桌菜。npm run dev 一键起前后端；注意它默认绑 localhost（IPv6），必须用 localhost:5173 访问而非 127.0.0.1
Ant Design 6.6现成的 React 组件库（按钮/表格/弹窗都造好了）。类比：宜家家具，买回来组装不用自己刨木头。表单、卡片、抽屉、消息提示。坑：v6 大量 API 改名（Alert 的 message→title、Space 的 direction→orientation），每加新组件跑一次 smoke 能抓到弃用警告
react-router-dom 7页面路由：根据网址决定显示哪个页面。类比：大厦楼层索引。登录/行程列表/新建/详情/设置五个页面
dayjs轻量日期处理库出发日期、按天算日期（addDays）

3.2 后端

技术一句话定义 + 类比在本项目怎么用
Node.js 22/24 + TypeScript让 JS 跑在服务器上的运行时；TypeScript 是带类型标注的 JS，写错字段名编译期就报错整个后端都是 TS；前端也用 TS
Express 5.2后端 Web 框架，把「网址→处理函数」组织起来。类比：餐厅前台，按单号分单。所有 REST 接口：/api/auth、/api/trips、/api/amap、/api/settings；JWT 中间件做登录校验
Prisma 7.10ORM——用「对象」操作数据库而不用手写 SQL。类比：你跟仓库管理员说人话，他去搬货。5 张表（见第六章）。注意 Prisma 7 三个非常规约定：①连接串不在 schema 里而在 prisma.config.ts；②客户端必须传 libsql 适配器；③CLI 必须钉 7.10.0（npm 的 latest 标签被上游指向 8.0 预发布版）
SQLite(libSQL) → Postgres数据库：一个文件就是一个库（开发期），上线换 PostgreSQL开发期零部署成本；用 @libsql/client 适配器（平台预编译包，规避了 better-sqlite3 那类本地编译问题——但 LangGraph 的 checkpointer 仍依赖它，见第八章）
jsonwebtoken(JWT)登录凭证：签一张防伪门票给前端，之后每次请求带上。登录成功签发 token；中间件校验；修改用户名后旧 token 自动换新
zod 4.6入参校验器：请求体字段对不对、类型对不对，它说了算。类比：机场安检。所有 POST 接口的 body 校验；也是 LangGraph 状态字段的定义方式

3.3 AI 与地图（本项目灵魂）

技术一句话定义 + 类比在本项目怎么用
OpenAI 兼容接口（BYOK）用户自己填模型地址和 Key（DeepSeek/通义等都兼容这套协议）。类比：手机不锁运营商，插谁的卡打谁的网。设置页填 baseUrl/modelName/apiKey；服务端用 AES-256-GCM 加密后入库，绝不明文存储；每次生成实时解密取用
@langchain/langgraph 1.4.15用「图（节点+边）」组织 AI 工作流的编排框架。类比：把 while 循环升级成一张可视化的流程图，且图能自动存档断点、能在任意节点暂停等人。整个生成编排：StateSchema 定义状态、三个主节点+条件边、interrupt 实现人工裁决、SQLite checkpointer 实现断点续跑。版本必须 --save-exact 钉死 1.4.15
高德开放平台（Web 服务 API）中国境内合规的地图数据源：地点搜索、路线规划、天气、地理编码。模型可调的 5 个工具的底层（见 5.2）；前端 JS API 渲染地图；所有坐标唯一来源
进程内 TTL 缓存把接口结果在内存里存一段时间，期内重复请求直接复用。类比：把常用菜抄在小黑板上，不用每次问后厨。地理编码 24h / POI 10min / 天气 30min / 路线 5min；同一时刻的相同请求做并发合并（只发一次真请求）；是控制高德配额与 QPS 限流的第一道防线
依赖铁律：能用平台预编译包就不引入需要本地编译的原生模块（better-sqlite3 是本项目唯一被迫引入的，它按 Node 大版本绑定二进制——Node 22 编译的产物在 Node 24 下直接加载失败，升级 Node 后必须 npm rebuild better-sqlite3）。关键依赖一律 --save-exact 钉死版本。

四、用户输入之后发生了什么（四步向导逐拆）

第 1 步：基本信息

1目的地城市 → adcode。用户输入「杭州」这样的城市名，但高德的 POI 检索、天气查询要的是 6 位行政区划编码（adcode）。所以输入框失焦后立即调高德地理编码接口：既拿到编码，又拿到城市中心坐标（供地图初始定位）。这一步是强制的——只拿城市名是查不准的。

2日期 / 天数（1-7）/ 人数 / 偏好多选（亲子、美食、文化…）/ 预算（人均或总价）/ 额外需求多选。额外需求不只是文案——里面的「不含爬山」「不含主题乐园」「不含夜爬」「节奏轻松些」会被 parseDayTypeBan() 解析成结构化黑名单，在代码层硬性拦截，不依赖模型自觉。

第 2 步：地图选住宿（锚点）

3页面内嵌高德 JS 地图（前端 Key），搜索酒店、点选一家，坐标存进 Trip 表。也可以选「还没定住宿」——此时图编排的第一个节点 resolveAnchor 会让模型调工具挑一个交通便利的中心区域，并把理由写进决策记录。锚点是整趟行程的地理中心：每天从住处出发、晚上回住处。

第 3 步：生成行程

4两个开关：逐天人工确认（每排完一天暂停等确认/驳回）和并行择优（每天并行两套方案供挑选，卡上明确提示「消耗与耗时约翻倍」）。点生成后：

  • 后端把 Trip 状态置为 generating，立刻返回 202，真正的生成在后台异步跑；
  • 若该行程 10 分钟内已在生成中，返回 409 拒绝重复触发（STALE_GENERATING_MS = 10 分钟，防止卡死状态无法重试）；
  • 前端进入轮询：每 2.5 秒 GET 一次行程详情，把 genProgress（进度文案）、genReview（待确认卡片载荷）、genDayIndex（已完成天数）渲染出来；
  • 期间可以关页面，生成在服务端继续；每天排完立即落库，失败可从断点继续。

第 4 步：查看与打卡

左列线圈本时间轴（时段分组：上午 1 个景点 + 餐饮，下午至晚上 1-2 个），右列高德地图画真实驾车路线（含住处往返闭环）。每个地点可点「换一个」，可手动打卡。

五、核心：AI 是怎么排行程的

5.1 先建立三个心智模型

模型（LLM）是什么角色：一个「会读题、会打电话查资料的参谋」，不是数据库。它负责理解需求、决定去哪怎么串；但每一家的坐标、评分、营业时间、车程，都必须由代码调高德接口获取。为什么？因为模型会「编」——它见过无数篇游记，能流利地写出一个不存在的店名和看似合理的坐标，地图上一画就飘到海里。本项目铁律：坐标只准来自高德 POI 返回值。实现方式是 POI 登记表（registry，一个 Map）：工具每查到一个地点就登记入册，行程条目只准引用册内的 poiId。
工具调用（tool calling）是什么：让模型能「打电话」的机制。我们把高德接口包装成 5 个工具（见下表），在提示词里告诉模型「你有这些电话可打」。模型输出「我要打 search_poi，参数是杭州、景点」——由代码真正执行后把结果喂回给它，如此往复直到它交出最终方案。类比：参谋自己不出门，但桌上有五部内线电话。
图编排（LangGraph）是什么：把「先干什么再干什么、失败怎么办、何时等人」画成一张节点+边的图，由框架驱动执行并自动存档。相比手写 while 循环，它白送三样东西：①检查点——每个节点跑完自动快照，进程崩了从断点恢复而不是从头再来；②interrupt——任意节点可以暂停等人类输入再继续；③条件边——「重试还是放弃」用图的走向表达而不是层层 if。

5.2 模型的 5 部内线电话（工具清单）

工具功能关键细节
search_poi按关键词/类别搜地点必须传 show_fields=business,photos 才拿得到评分、人均、营业时间、照片——v5 接口不声明就不返回（transit 接口漏传 show_fields=cost 曾导致耗时恒为 0，见第八章）
search_nearby在某点周边搜（换点候选、找餐厅）带直线距离；换点时按半径梯度 1500→3000→5000 米逐级放宽
get_route两点间真实路线show_fields=cost,polyline；驾车给通勤分钟与折线（画地图）；公交给公共交通耗时；响应无 paths 时必须当错误抛出重试，否则解析成 0 且被缓存 5 分钟
get_weather天气预报高德只有约 4 天预报，超出窗口返回空数组——提示词明确告知模型「按天气未知处理，不要编造」
get_city_center城市中心坐标锚点推荐时定位用

单天工具循环上限 MAX_DAY_TOOL_ROUNDS = 14 轮——防止模型陷入「查了又查、不给结果」的死循环；超限抛错进入重试。

5.3 一天的生成流程（planDay 节点内部）

1组装提示词：需求+日期天气+住处+近 20 个去过的地名+昨天体裁强度+已用夜生活类别（+用户驳回意见，若有）
2模型带工具循环（≤14 轮），期间真正调高德查地点/路线
3解析 JSON（失败则带着错误信息让模型重答一次，再失败才抛错）
4规则校验 validateDay：评分门槛 / 营业时间 / 黑名单 / 跨天去重 / 夜生活类别 / 天型传导
5通勤体检 optimizeCommute：逐段真实驾车时间，>40 分钟自动换点；公交估算并行获取
6交互模式：挂起等裁决 → commitDay 落库；全自动：直接 commitDay

5.4 硬约束清单（全部真实数值，代码层强制）

约束规则为什么这么定
坐标来源只准引用 POI 登记表内的 poiId，模型绝不提供坐标模型编坐标会飘到海里
评分门槛景点 < 4 剔除；餐厅 < 3.5；评分缺失(null)一律放行免费公园大多无评分，硬卡会误杀；餐厅门槛高德数据更松
营业时间与所排时段重叠 ≥ 60 分钟，否则剔除；重叠够但「到达后剩余 ≤ 210 分钟」只标注仓促；餐厅完全不校验「仓促」用剩余时长而非重叠时长（下午窗天然 4.5h，按重叠 17:00 关门都算充裕）；高德餐厅时间最不准
营业时间解析按出现顺序取首尾，不能 min/max；尾 ≤ 首则跨夜 +24h夜市写「18:00-02:00」，min 会把 02:00 当开门时间，方向整个反了
每日景点上限normal 3；theme_park / hike / night_hike 1；recovery 2；餐厅不计入体裁决定节奏
天型传导夜爬 > 主题乐园 > 徒步 强制升级；夜爬/高强度次日强制 recovery判定顺序：规则表强制 → 模型提议兜底 → 统一过用户黑名单（黑名单只挂在第一层会让模型提议路径绕过）

重试与跳过单天失败自动重试 2 次，超限跳过该天推进（不死循环）；LangGraph 递归上限 25 是最后的安全网刻意「重试当前天」而非「回退前一天」——回退会覆盖已确认结果

5.5 人工裁决（interrupt 的三种形态）

5.6 断点续跑（checkpointer）

SQLite checkpointer（文件在 .debug/，已 gitignore）以 tripId 为 thread_id，每个超级步自动快照图状态。进程崩溃重启后用同 thread_id 重新 invoke 即可从断点节点继续——手写版只能靠 Prisma「天级」恢复（当天排到一半全丢）。注意：checkpointer 只存可 JSON 序列化的状态，registry（Map）、凭证、天气这些放闭包里（buildAgentGraph(ctx) 每次生成构建一次，天然会话隔离）。

6.2 数据大小的确定原则

  • 能算出来的不存：通勤分钟数随路况变，只在生成时算一次存进条目，地图路线实时重查（5 分钟缓存）；
  • 列表性的存 JSON 字符串（preferences/extraNeeds/photos/weather/genDecisions）——SQLite 下比建关联表省事，且这些数据永远是整体读写、不会按元素查询；genDecisions 设 50 条上限防无限增长；
  • 大对象放文件/缓存不进库：POI 登记表在内存（生命周期=一次生成），图片上传放磁盘 /uploads；
  • 卡上限的地方都有明确数值：单天工具轮次 14、决策 50 条、重试 2 次、/photos 3 张、意见 500 字；
  • 枚举用字符串+注释约定（status/dayType/slot/intensity），前端用常量表映射展示文案。

6.3 数据从哪来到哪去（高德配额防御）

所有外部数据请求都过三层：①进程内 TTL 缓存（地理编码 24h / POI 10min / 天气 30min / 路线 5min）；②并发合并（同一瞬间的相同请求只发一次真调用）；③错误分级——业务错误（Key 无效、配额尽）不重试直接抛，网络/超时/非 2xx 自动重试 2 次，仍失败再走兜底（直线估算）。日志里绝不打印完整请求 URL（里面带 Key）。

七、前端功能实现细节

纸质手帐主题（全局一套变量）

整体隐喻「旅行手帐」：行程列表是横躺的牛皮纸书签（右端 clip-path 切 V 形口 + 左端穿线孔，厚 91px），详情页左列是线圈本（纸色底+横向格线+红色页边线+24 个金属环），条目是便利贴（浅底深墨、轻微倾斜、顶端两角半透明胶带）。

  • 核心做法：把 antd 全局 token（colorBgContainer/colorText/colorBorder）换成「纸色+墨色」（白天 #fbf7ec/#3d3527，黑夜 #242a33/#d2d9e2），所有组件自动获得纸质感，调色只改一处；
  • 结构性颜色（纸色/胶带/书签）写成 index.css 的 CSS 变量，:root[data-theme='night'] 里覆盖——组件侧零 if(isNight)；
  • 便利贴倾斜走 --tilt 变量而非行内 transform（行内优先级最高，hover 就永远盖不掉）；淡彩底按序号轮换不用随机（随机会在滚动时变色像 bug）；
  • 便利贴底色与墨色必须同源派生（usePaperTheme）——曾出现底色读 DOM 属性、墨色读 React 状态的一帧错位，黑夜切白天瞬间浅底配浅字。

生成页防抖动三件套

  • scrollbar-gutter: stable：滚动容器提前预留滚动条槽位，浮层开合时页面不左右抖；
  • overscroll-behavior: contain：下拉列表滚到底后滚轮事件就地消化，不冒泡带动整页；
  • 表单容器 max-height + overflowY:auto + 固定底部按钮：字段再多也只在卡片内滚，步骤条/顶栏纹丝不动。

打卡与「换一个」

打卡纯手动：点按钮写 checkedAt，未打卡空心圆点、已打卡实心+对勾角标+卡片置灰，当天当前目标放大/脉冲，默认只显示当天标记。「换一个」调后端：排除目标自己 → 半径梯度搜同类 → 硬规则过滤 → 两段通勤之和排序 → 抽屉展示前 6 个候选。

八、错误编年史：26 个真实踩坑与解决措施

以下全部是本项目真实发生过的问题。按主题分组，每条都是「现象 → 根因 → 解决 → 教训」。

8.1 React 与前端

① 详情页整页白屏：Rendered more hooks than during the previous render

根因：新增的 hook 写在了 if (loading) return 之后——第一次渲染走 loading 分支少执行几个 hook、数据到达后多执行几个，React 的 Hook 顺序契约直接崩。
解决：所有 hook 挪到提前 return 之前；无法挪的把依赖数据做成可空安全版。
教训：这类错误静态类型检查完全查不出来，只有真实渲染才暴露。给组件加 hook 时先确认它落在哪个提前 return 之前。

② 端到端点击「点不到」且不报错

根因：表单加高后目标元素落到视口折叠线以下，坐标跑出视口，CDP 鼠标事件打在空气上——静默失败。
解决：clickReal() 发事件前先 scrollIntoView。

③ antd 6 Select 打不开下拉 / 断言下拉选项漏项

根因：antd 6 不再响应合成 MouseEvent（element.click() 无效），必须 CDP 发真实鼠标事件；且 6 已移除 .ant-select-selector（换 .ant-select-content）；下拉是虚拟滚动（11 项首屏只渲染 10 项），断言前必须先滚到底；选项文本用 textContent 而非 innerText（视口裁剪）。

④ 切主题瞬间便利贴「浅底配浅字」

根因：底色读 documentElement.dataset.theme（DOM 属性，useEffect 里才更新），墨色读 React 主题状态——两者有一帧错位。
解决：两套颜色都从 usePaperTheme() 同源派生。教训：同一视觉的两个值必须同源，不允许两种读取路径。

⑤ 浮层开合页面左右抖动 / 下拉滚到底带动整页

根因：滚动条占位在锁滚动时计算不一致；虚拟列表滚到底后 wheel 事件冒泡到外层。
解决：scrollbar-gutter: stable + overscroll-behavior: contain + 浮层 max-height。

⑥ 行内 transform 锁死 hover 动效

根因：便利贴倾斜用行内 style.transform，优先级高于任何 CSS 规则，「按平」交互失效。
解决：倾斜走 CSS 变量 --tilt。

8.2 LangGraph 与 AI 编排

⑦ 「找不到生成上下文」

根因：用 WeakMap 以 config 对象为 key 绑定会话上下文——但 LangGraph 内部会 clone config，引用对不上。
解决：改为 buildAgentGraph(ctx) 闭包捕获，每会话构建一次图，天然隔离。教训：框架文档没说的内部行为（config 会被重建）只能实测发现。

⑧ ReducedValue 类型报错

根因：JS 版 1.4.x 的 StateSchema 里累积字段必须 new ReducedValue(zodSchema, {reducer})——第一个参数是 zod schema，直接传默认值不行；文档示例与实际类型定义有出入，以 node_modules 里的 .d.ts 为准。

⑨ review 模式误报「生成失败」

根因：interrupt 让 invoke 提前返回（带 __interrupt__），catch 分支把它当普通失败设了 status=failed。
解决：显式检查 __interrupt__——中断不是失败，是把「待确认摘要」写进 genProgress/genReview 后正常返回。

⑩ 重复裁决导致同一天连排 4 次

根因：图正在重排时（无挂起中断）又收到 resume，LangGraph 不报错而是从上一个检查点重跑节点。
解决：resume 前用 getState 检查确实存在挂起 interrupt，否则静默忽略；恢复入口先清 genReview 消掉前端竞态。

⑪ 双方案只剩一个时崩溃：reading 'day' of undefined

根因：优缺点对比硬性取 shown[1-i].day，只剩一个候选时越界。
解决：候选 < 2 时降级为单方案确认。教训：展示数据依赖 N 个对象时，N 是运行时事实不是编译期假设。

⑫ 路由死循环烧到 25 步上限

根因：条件边在特定状态下永远走回同一节点，LangGraph 递归上限 25 触发 GraphRecursionError。
解决：把「超限跳过推进」的逻辑放进节点自身（节点有状态、条件边是纯路由函数不能改状态）；把递归上限当作最后的安全网写进测试断言。

8.3 高德接口与数据

⑬ 「通勤约 0 分钟」的虚假结论

根因（两层）：①路径规划偶发返回「状态成功但 paths 为空」（限流边缘），代码不报错、duration 解析成 0、还被缓存 5 分钟；②查询失败返回 null，统计时 null ?? 0 当 0 参与对比。
解决：无 paths 抛 RetryableError；失败退回直线估算（×1.4 绕行 ÷ 417 米/分钟）；统计只对拿到的数据求和、全缺失保持 null；对比遇缺失输出「数据暂缺」而非硬比。
教训：「解析失败给默认值 0」是数据陷阱——0 在比较里是最优值。缺失就该是 null，宁缺毋错。

⑭ 公交耗时恒为 0

根因：高德 v5 接口必须显式传 show_fields=cost 才返回耗时，transit 分支没传（distance 正常返回，极具迷惑性）。
解决：补上参数；探针直连接口验证 2512 秒 ≈ 42 分钟。教训：怀疑接口时写 20 行探针直连，比读十遍业务代码快。

⑮ 夜市营业时间方向反转

根因：解析「18:00-02:00」时用 Math.min 取开门时间，把 02:00 当成了开门。
解决：按出现顺序取首尾，尾 ≤ 首则跨夜 +24h。

⑯ 换点逻辑拿不到评分和类型

根因：asPoi() 兜底路径会把 rating/type/typecode 抹成空值，下游校验全部失效。
解决：优先从 registry 取完整 POI，兜底时也尽量保留字段。

⑰ 高德偶发连接中断（HTTP 000 / SSL eof）

根因：网络波动，尤其并行生成时 QPS 处于限流边缘。
解决：错误分级——业务错误（AmapError，带 infocode）不重试；网络类（RetryableError）自动重试 2 次；仍失败走直线估算或跳过。不要把偶发中断误判为 Key 或参数问题。

8.4 工程与环境

⑱ better-sqlite3 加载失败：NODE_MODULE_VERSION 127 vs 137

根因：原生模块按编译时的 Node 大版本绑定，工具环境 Node 22 编译、用户终端 Node 24 运行（反之亦然）。
解决：谁的 Node 变了谁 npm rebuild better-sqlite3；且该模块是惰性加载（只在生成触发 checkpointer 时 require），所以页面能开、一点生成就报错，极具迷惑性。

⑲ npm 的 latest 标签不可信

根因：prisma 的 latest 被上游指向 8.0.0-rc 预发布版。
解决：关键工具链依赖一律 --save-exact 钉死。

⑳ npm 安装脚本被拦截

根因：沙箱 npm 有 allow-scripts 策略，拦截 install/postinstall（better-sqlite3 的 prebuild、esbuild 的 postinstall）。
解决：优先选平台预编译包（@libsql/client、@esbuild/win32-x64）；含原生编译的安装交给用户本机终端。

㉑ 端口被旧进程占用

根因：改了代码但端口上跑的还是旧进程——请求新路由 404、老路由正常即是判据。
解决：Git Bash 里 MSYS_NO_PATHCONV=1 taskkill /F /PID x（不带前缀会把 //F 当路径转换）。

㉒ Vite 访问 127.0.0.1 连不上

根因：Vite 默认绑 localhost（IPv6）。用 localhost:5173 访问。

㉓ 后台服务留不住

根因：沙箱里 nohup/background 启动的进程在命令结束时被清理，下次调用 ECONNREFUSED。
解决：启动、等待、验证、读日志写进同一条 Bash 命令内完成。

㉔ Prisma 7 三个非常规约定

连接串在 prisma.config.ts 不在 schema；客户端必须传 libsql 适配器（裸 new PrismaClient 直接崩）；CLI 必须在 apps/server 目录下执行且钉 7.10.0。

㉕ Prisma Json 列的 null 陷阱

根因：Prisma 对 Json 列置空要 Prisma.DbNull，直接 null 会校验失败。
解决：genReview 故意用 String? 存 JSON.stringify 文本。

㉖ 前后端日志都说「成功」但数据是错的

根因：见⑬——每一层都「成功」了，只有最终展示的 0 分钟暴露问题。
解决：给数据链路加「探针脚本」直连最底层接口，逐层对照。

九、错误处理哲学：三条原则

原则一：错误分级，区别对待。不是所有错误都值得重试——业务性错误（Key 无效、参数错）重试一万次也没用，直接把可读的原因抛给用户；只有瞬时性错误（网络抖动、限流边缘）才配自动重试。本项目把错误分成 AmapError（不重试）与 RetryableError（重试 2 次），并且把可读的错误信息一路带到前端（genError 字段），而不是让用户看到「出错了」。
原则二：宁缺毋错，缺失绝不是 0。数据拿不到时，唯一诚实的表示是 null + 前端展示「未知」。绝不允许「解析失败给默认值 0」——因为 0 在「谁更短、谁更便宜」这类比较里是最优值，缺失会伪装成冠军。同理：评分缺失放行而不是按 0 分剔除；公交查不到显示「未知」而不是拿驾车时间冒充。
原则三：不报错的失败最危险。这轮最贵的三个坑——点击落到视口外、浮层重入导致重复重排、paths 为空解析成 0——全部没有任何报错。对策是两条：①关键路径埋「结构性证据」的自检（smoke 77 条断言 + check 65+19 条），断言的是数据形状而非界面文案（文案断言曾因渲染时序产生假失败）；②对框架的隐式行为（config 会 clone、无中断时 resume 会重跑）永远用最小探针实测，不信文档也不信记忆。

文档小结：这个项目的本质是「用代码给 AI 立规矩」——模型负责创造性与决策（去哪、怎么串、怎么改），代码负责事实与底线（坐标从哪来、评分够不够、通勤多远、何时该问人、错了怎么办）。所有复杂度都围绕这条主线生长：数据不可信所以建准入规则，用户要掌控所以建人机协作，流程会中断所以建检查点。理解了这条主线，每一处代码细节都有了归属。
